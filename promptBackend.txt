# PROMPT BACKEND — Plateforme SaaS Multi-Tenant de Location de Voitures (Tunisie)

## Contexte & Stack

Tu es un développeur NestJS senior avec 10 ans d'expérience. Tu dois construire le backend complet d'une plateforme SaaS de location de voitures en Tunisie avec les caractéristiques suivantes :

- **Architecture** : Multi-tenant (shared database, shared schema avec `agency_id` comme discriminant)
- **Backend** : NestJS + TypeScript + TypeORM + PostgreSQL
- **Auth** : JWT (access token 15min + refresh token 7 jours)
- **2 types d'usages** :
  1. **Dashboard Agence** : chaque agence = 1 tenant, avec plusieurs users internes (owner / manager / agent)
  2. **Marketplace publique** : visiteurs et clients qui cherchent une voiture, toutes agences confondues

## Implémentation — Points critiques

### 1. Isolation Multi-Tenant (OBLIGATOIRE)

Crée un `TenantInterceptor` qui :
1. Extrait le `agency_id` du JWT payload (claim `agencyId`)
2. L'attache à `request.agencyId`
3. **Tout service tenant-scoped** reçoit `agencyId` en paramètre et l'ajoute SYSTÉMATIQUEMENT à chaque `findOne`, `findAll`, `update`, `delete`

```typescript
// Exemple pattern dans tous les services tenant-scoped
async findCarById(carId: string, agencyId: string): Promise<Car> {
  const car = await this.carsRepo.findOne({
    where: { id: carId, agencyId }, // ← TOUJOURS les deux
  });
  if (!car) throw new NotFoundException('Car not found');
  return car;
}
```

**Ne jamais** faire un `findOne({ where: { id: carId } })` seul dans un contexte dashboard.

### 2. Auth — JWT Double Token

- **Access token** : 15 minutes, payload `{ sub: userId, agencyId?, role, agencyRole? }`
- **Refresh token** : 7 jours, stocké en DB hashé (bcrypt) dans `users.refresh_token_hash`
- `POST /auth/register` → crée user, envoie email vérification
- `POST /auth/login` → retourne `{ access_token, refresh_token, user }`
- `POST /auth/refresh` → valide refresh token en DB, retourne nouveau access token
- `POST /auth/logout` → invalide le refresh token en DB (met à null)
- `POST /auth/forgot-password` → génère token 1h, envoie email
- `POST /auth/reset-password` → valide token, hash nouveau mot de passe
- `GET /auth/verify-email/:token` → vérifie email

**Login agence** : quand un `agency_user` se connecte, le JWT doit embarquer `agencyId` + `agencyRole` pour que le TenantInterceptor puisse les extraire.

### 3. Module Marketplace (public, sans auth)

```
GET /marketplace/cars
  ?governorate=tunis
  &category=suv
  &start_date=2024-06-10
  &end_date=2024-06-15
  &min_price=50
  &max_price=200

  &page=1
  &limit=12

GET /marketplace/cars/:id         ← détail voiture + agence info
GET /marketplace/agencies         ← liste agences actives avec filtres
GET /marketplace/agencies/:slug   ← profil public d'une agence + ses voitures
```

La requête de disponibilité doit exclure les voitures qui ont :
1. Un `booking` avec `status IN ('confirmed','in_progress')` et dont `start_date <= end_date_param AND end_date >= start_date_param`
2. Un `car_availability_block` sur les mêmes dates

```sql
-- Voitures disponibles sur une période
SELECT c.* FROM cars c
WHERE c.status = 'available'
AND c.agency_id IN (SELECT id FROM agencies WHERE status = 'active')
AND c.id NOT IN (
  SELECT car_id FROM bookings
  WHERE status IN ('confirmed','in_progress')
  AND start_date <= :endDate AND end_date >= :startDate
)
AND c.id NOT IN (
  SELECT car_id FROM car_availability_blocks
  WHERE start_date <= :endDate AND end_date >= :startDate
)
```

### 4. Module Bookings

**Marketplace (public)** :
- `POST /marketplace/bookings` → crée une demande (status = 'pending'), envoie email à l'agence + confirmation au client
- `GET /marketplace/bookings/:reference` → status de la demande (par référence + email, sans auth)

**Dashboard Agence** :
- `GET /dashboard/bookings` → liste avec filtres (status, date, search)
- `GET /dashboard/bookings/:id` → détail
- `PATCH /dashboard/bookings/:id/confirm` → confirme (status → 'confirmed'), notifie client
- `PATCH /dashboard/bookings/:id/reject` → rejette avec raison, notifie client
- `PATCH /dashboard/bookings/:id/start` → démarre (status → 'in_progress'), met car.status → 'rented'
- `PATCH /dashboard/bookings/:id/complete` → termine (status → 'completed'), met car.status → 'available', déclenche demande d'avis
- `PATCH /dashboard/bookings/:id/cancel` → annule
- `GET /dashboard/bookings/calendar` → vue calendrier (toutes voitures + réservations)

**Espace Client (auth required)** :
- `GET /client/bookings` → historique réservations du client connecté
- `DELETE /client/bookings/:id` → annulation par le client (si status = 'pending' ou 'confirmed' et J-2 minimum)

### 5. Guards & Roles

```typescript
// 3 niveaux de guards à combiner
@UseGuards(JwtAuthGuard)                          // Authentifié
@UseGuards(JwtAuthGuard, AgencyMemberGuard)       // Membre d'une agence
@UseGuards(JwtAuthGuard, AgencyMemberGuard, RolesGuard)
@Roles('owner', 'manager')                        // Rôle agence spécifique
```

`AgencyMemberGuard` :
1. Récupère `agencyId` depuis les params de route ou le JWT
2. Vérifie que le `user.id` est dans `agency_users` avec `status = 'active'` pour cet `agencyId`
3. Attache `request.agencyRole` pour le `RolesGuard`

## Règles de sécurité à implémenter

1. **Rate limiting** : `@nestjs/throttler` — 100 req/min globalement, 5 req/min sur `/auth/login` et `/auth/forgot-password`
2. **Helmet** : headers HTTP sécurisés
3. **CORS** : whitelist des domaines frontend uniquement
4. **Validation globale** : `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })` sur l'app
5. **Sanitisation** : pas de données sensibles dans les logs (password, tokens)
6. **Pagination obligatoire** sur toutes les listes (default limit: 20, max: 100)
7. **Soft delete** : ajouter `deletedAt` (TypeORM `@DeleteDateColumn`) sur `cars`, `agencies`, `users` plutôt que supprimer en dur
